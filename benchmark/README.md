# benchmark · 用对照集审验工具

单元测试证明「代码按设计运行」，这里证明「设计本身对不对」。

```bash
python run.py              # 跑全部
python run.py --verbose    # 看每个场景实报了什么
python run.py --case vat   # 只跑一个
```

## 每个 case 长什么样

```
cases/<slug>/
├── expected.json     # 标准答案
└── input/            # 输入文件（CSV / MD / DOCX / XLSX）
```

`expected.json`：

```json
{
  "name": "进项税勾稽 · 税率差异与异常票",
  "tool": "ledger",
  "argv": ["--voucher", "{input}/凭证明细.xlsx", "--invoice", "{input}/发票.xlsx", "--out", "{out}", "--json"],
  "report": "{out}/vat-reconcile.json",
  "must_find": ["9%", "异常"],
  "must_not_report": ["13%", "6%"],
  "notes": "9% 差 5 元；那张 8.3% 的发票应归为异常税率；13% 和 6% 两边完全一致"
}
```

- `must_find`：必须报出来的（漏了 = 漏报，最危险）
- `must_not_report`：绝不能报的（报了 = 误报，久了没人看）

比对时忽略空格、千分位逗号和标点，所以 `120,000` 和 `120000` 视为同一个值。

## 真实数据 case

七组数据全部来自公开接口，用 `make_real_cases*.py` 可重新抓取：

| Case | 来源 | 人工核对后的标准答案 |
|---|---|---|
| real-wb-gdp | 世界银行 NY.GDP.MKTP.CD | CN +21.8%、US +30.1%、DE +15.8%、JP −15.5% |
| real-wb-population | 世界银行 SP.POP.TOTL | BR +1.2%、IN +2.5%、US +1.6%；CN 仅 −0.03%，在容差内不报 |
| real-wb-inflation | 世界银行 FP.CPI.TOTL.ZG | DE 0.14%→5.95%、JP −0.025%→3.27%（含负值） |
| real-wb-unemployment | 世界银行 SL.UEM.TOTL.ZS | US 8.06%→3.64%、IN 7.86%→4.17% |
| real-github-tag | GitHub API，vuejs/core 两个 tag 的 package.json | 13 项删除、8 项新增、34 项版本变化 |
| real-npm-mirror | npmjs.org vs npmmirror.com，express@5.0.0 | 32 个依赖完全一致（expect_empty） |
| real-fx | frankfurter.app，CNY→USD/EUR/JPY | 波动 0.09%–0.93%，需把容差调到 0.01% |

原始 JSON 留在 `raw/`，每个数字都能复查。

**这七组里有四组暴露了我的 case 配置错误**——不是工具错：
- 人口：CN 只变 0.03%，我要求它必须报，但工具按 1% 容差忽略是对的
- vue：报告文件名里的点被正规化成下划线，我写错了路径
- 汇率：默认 1% 容差会全部忽略，必须显式调小
- 世界银行国家码：返回的是 `CN`/`US` 两位码，不是 `CHN`/`USA`

写 benchmark 的价值一半在于此：**你会被迫把「我以为应该报」和「实际该报」分清**。



## 抓不到真实数据时，怎么编

财务、体检、个人能力这些场景涉及隐私，公开数据抓不到。做法是**编出真实业务里会出现、但工具容易翻车的复杂度**：

| 编造的陷阱 | 真实对应 | 结果 |
|---|---|---|
| 红字（负数）发票 | 退货/折让冲销，真实凭证里很常见 | **抓到真缺陷**：三份脚本都 `if amount <= 0: continue`，红字被丢掉，13% 税额虚高 50 元 |
| 铁路票与专票混在同一税率 | 9% 计算抵扣与 9% 专票分组 | 通过 |
| 数值恰好压在切点上（TC 5.2、血糖 6.1、尿酸 420） | 体检报告里界值很常见 | **抓到真缺陷**：用 `value > upper` 判断，5.2 被判成「合适」，而指南写的是 <5.2 才合适 |
| 变更记录表里写「内孔 原值 Ø32 新值 Ø36」 | 每个项目的 CR 记录都长这样 | **抓到两个缺陷**：变更记录被当成待更新（误报）；「内孔约 Ø32」解析不出（漏报） |
| 交付包把 图A.png 改名成 图A_v2.png | 版本迭代加后缀是常态 | **抓到缺陷**：改名被报成「删了一个、加了一个」 |
| 两期报告主键大小写不同（M-1001 vs m-1001） | 换了数据源就会发生 | **抓到缺陷**：同一件持续问题被判成「上期解决 + 本期新增」 |

红字这个 case 的价值：它不是「造一个工具能过的题」，而是造了一个**当时会翻车的题**，然后逼出修复（三处 `<= 0` 改成 `== 0`，`classify` 取绝对值）。

编题的原则：
1. 陷阱必须来自真实业务，不是为了黑工具
2. 标准答案要能手算（凭证 1300、发票 1300−50、差 50）
3. 抓到缺陷就修工具、补单测，然后保留这个 case 做回归

## 这个 1.00 说明什么、不说明什么

**说明**：在这 5 个场景上，工具没有漏报也没有误报，方向和阈值是对的。

**不说明**：
- case 是我自己设计的，**有幸存者偏差**——我会不自觉地设计工具能过的数据
- 场景数少（5 个），覆盖不了真实资料的混乱程度
- 没测对抗性输入：同物异名、多型号混排、跨期、口径未统一

**3 个对抗 case 也不够狠**——我知道工具有 CODE_RE、to_base、按主键对齐这些机制，所以设计的陷阱都是它们能过的。真正对抗的是我没预料到的情况。

**真正有说服力的 benchmark 应该来自真实数据**：拿一份跑出过问题的真实资料，标注「应该报什么」，再跑一遍。那才叫审验。

## 怎么加一个 case

1. 建 `cases/<slug>/input/`，放输入文件
2. 手算一遍正确答案（这一步不能省）
3. 写 `expected.json`：`must_find` 用子串关键词，`must_not_report` 填「看起来像问题但其实正常」的项
4. `python run.py --case <slug> --verbose` 看实报了什么

**漏报优先于误报**：一个漏报会让用户以为没问题，一个误报只是多看一眼。

## 已知陷阱（写 case 时踩过的）

- 期望里的文件名要和输入一致（`汇报.md` vs `汇报备注.md`）
- 金额在原文里可能带千分位逗号，比对要归一化
- 工具的「覆盖缺口（low）」不该算误报——只有 high 级冲突才计入
- 输出目录在输入目录内时会被自己扫到，case 要把 `{out}` 放在 input 之外
