# spec-consistency · 产品资料一致性审计

**同一套参数写在五份材料里，必然会出现对不上的地方。** 规格书写 512 Wh，宣传页写 500 Wh，报价单沿用上一版，官网抄了宣传页——每一份单看都没问题，放在一起就是错的，而客户往往比你先发现。

这个 skill 检查的不是"一份文档写得好不好"，而是**一组文档之间是否自相矛盾**：跨 Word / PPT / Excel / Markdown，把每个 `参数：值 单位` 抽出来对齐，把对不上的地方连原文一起列给你。

`MIT` · `Python 3.10+` · `35 个离线测试` · `零 API 调用`

---

## 30 秒看效果（不需要任何 API Key）

```bash
python scripts/spec_audit.py demo
```

它会现场造一套"产品资料包"——规格书.docx、宣传页.pptx、报价单.xlsx——里面埋了三处真实矛盾，然后审计：

```
documents: 3 · parameters: 6 · comparable: 4
findings: 3 high / 3 medium / 2 low
  [high] 电池容量: 512Wh vs 500Wh vs 512Wh
  [high] 满载续航: 50分钟 vs 45分钟
  [high] 整机重量: 6kg vs 6.2kg vs 6.2kg
```

报告长这样（真实输出，节选）：

```markdown
### 2. `满载续航` · HIGH

跨文档数值不一致：时间基准下最大相差 10.0%

| 文档 | 值 | 原文 |
|---|---|---|
| 宣传页.pptx | 50 分钟 | 满载续航：50 分钟 |
| 规格书.docx | 45 分钟 | 满载续航：45 分钟 |

**建议**：确定唯一真相（通常以规格书为准），其余文档以它为准同步。
```

注意"原文"那一列：**每一条结论都带着出处句子**，你可以直接判断这到底是真矛盾，还是两个不同型号。

## 它具体查什么

| 检查 | 例子 | 级别 |
|---|---|---|
| 跨文档数值不一致 | 规格书 6.2 kg vs 宣传页 6.0 kg | 高 |
| 文档内部自相矛盾 | 报价单里同一个参数两个值（通常是两个 SKU） | 中 |
| 计量口径不同 | 一个写 Wh，一个写 % | 中 |
| 单位写法不统一 | 45 分钟 vs 45 min（数值等价） | 低 |
| 参数只在部分文档出现 | 充电时长只在规格书里有 | 低 |

数值会换算到同一基准再比：`6.2 kg` 和 `6200 g` 算一致，`6.0 kg` 和 `6.2 kg` 算冲突（默认容差 0.5%）。

## 版本对比：V1 → V2 到底改了什么

```bash
python scripts/spec_audit.py versions \
  --from-dir ./pkg_v1 --to-dir ./pkg_v2 \
  --changelog ./pkg_v2/11_变更单_v1到v2.md -o reports
```

输出三件事，按重要性排序：

1. **哪些参数变了**——旧值、新值、变化幅度
2. **哪些变化变更单里没提**——最容易在交付时变成惊喜的那部分
3. 哪些参数新增/消失（默认折叠，`--show-added` 展开）

如果参数写在同一个表格的版本列里（`| 项目 | V1 | V2 |`），改成一个命令：

```bash
python scripts/spec_audit.py versions -d ./docs --from V1 --to V2
```

真实跑一套整改资料的输出（节选）：

```
pkg_v1 → pkg_v2: 6 项变化
  立柱中心距: 124 mm → 128 mm  (+3.2%)
  膝点电流: 71 A → 75 A  (+5.6%)

变更单覆盖：已提及 5 / 6，未提及 1
  I_knee: 71 A → 75 A
```

规则：**表格里的值优先于正文里的值**（表格是规格，正文是讨论）；换算后相等的单位差异不算变化（`6200 g` = `6.2 kg`）。

它读不了正文里手写的箭头（`内孔 Ø32→Ø36`）。如果一版的改动只写在句子里，先在文档里补一张对照表——那张表本来也是评审要看的东西。

## 怎么用

```bash
# 把一套资料放进一个文件夹
python scripts/spec_audit.py scan ./产品资料 -o reports

# 当 CI 门禁：有高危冲突就失败
python scripts/spec_audit.py scan ./产品资料 -o reports --fail-on high

# 生成报告 + JSON（JSON 里带每条的原文和位置）
cat reports/spec-consistency.md
```

支持 `.docx` / `.pptx` / `.xlsx` / `.md` / `.txt` / `.csv`，自动跳过 `.git`、`node_modules`、`reports`。
两种表格布局都能读：键值表（`参数 | 规格`）和宽表（`型号 | 电池容量 | 单价`）。

## 它查不到什么（重要）

- **图表、图片、PDF 里的数字**：导出成 docx/xlsx 再查，或者接受这个盲区
- **数字背后的真假**：它只判断"文档之间是否一致"，不判断"这个参数对不对"
- **不同条件的同一指标**：`满载续航 45 分钟` 和 `最长续航 50 分钟` 不冲突——所以参数名里要带条件
- **同义术语**：`整机重量` 和 `净重` 默认会被当成两个参数，需要在脚本的 `SYNONYMS` 里登记

所以它给你的是一份**待判断清单**，不是判决书。判断"哪个值才是真的"仍然是人的工作——通常以规格书为准，但"宣传页三份都写 500"不代表 500 对。

## 和"文档版本对比"有什么区别

版本 diff 告诉你"这一句改了"；一致性审计告诉你"**这两个文件在同一个事实上给出了不同的值**"——跨格式、跨文件名、跨团队写的那几份。前者是编辑工具，后者是发布前的体检。
